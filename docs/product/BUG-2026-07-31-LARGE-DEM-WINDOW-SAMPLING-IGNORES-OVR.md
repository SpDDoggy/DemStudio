# BUG-2026-07-31：大 DEM 窗口采样忽略 OVR

## 状态

已修复并建立回归闸门。

## 现象

31,984 × 18,495 的 FRMM GeoTIFF 已配有七级外部 `.ovr`，但 LOD 窗口请求仍逐块读取主 TIFF。1024 档完整基座构建会解码 17,637 个分块并发生 17,125 次缓存淘汰，构建约 5.65 秒。

## 根因

初始预览会读取 `.ovr`，窗口采样路径却始终重新打开主 TIFF。显示概览与 LOD 数据源选择是两条独立调用链，原有分块缓存又只以 TIFF 内部 chunk index 为键，无法安全缓存多个金字塔层。因此，已有 OVR 只缩短首屏预览，不能减少后续基座和精化的主图解压。

## 修复

- 打开数据集时发现并校验外部 OVR 图像层。
- 每个窗口选择仍能覆盖目标输出密度的最粗层，只允许降采样，禁止从过粗 OVR 升采样。
- 主图坐标按两端点对齐映射到 OVR 坐标，窗口范围和公开输出尺寸保持不变。
- OVR 打开、索引或尺寸校验失败时回退主 TIFF。
- 全局和请求内缓存使用“金字塔层命名空间 + chunk index”键，防止跨层误命中。

## 精度语义

OVR 是 GDAL 生成的降采样数据。其高程聚合比主图上的少量抽头采样更抗混叠，但 NoData 边缘拓扑不承诺与旧路径逐三角形相同。真实样例 1024 档的顶点数保持 698,922，三角形由 769,158 变为 765,649（约 -0.46%）；人工对比截图未见轮廓或地形细节退化。验收依据是固定源文件哈希、完整 64 基座、22 个空瓦片、有效覆盖、有限高程、无接缝和视觉基线，不使用旧三角形数作为 OVR 正确性的唯一判据。

## 永久回归闸门

- Rust 单元测试验证 4/5/17 像素目标分别选择 4/8/主图，证明“最粗但足够”和“不升采样”。
- `verify-frmm-real-tif.ps1` 固定真实 TIFF SHA-256，并对 1024/2048/4096 检查完整覆盖、LOD 驻留和最终 Core 缓存统计。
- 1024 最多解码 256 块；2048/4096 最多解码 1024 块；任何缓存淘汰都判失败。

## 回滚

回滚 `FileRasterSource` 发现、窗口 OVR 选层和缓存命名空间改动即可恢复主 TIFF 采样。无需迁移 TIFF、OVR、PAM、设置、IPC 或最近文件。
