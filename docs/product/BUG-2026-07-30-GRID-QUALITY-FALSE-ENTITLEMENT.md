# BUG-2026-07-30：大范围网格质量虚标与顶点不足

## 状态

根因修复已完成，并通过指定 31,984 × 18,495 GeoTIFF 的同一 Release EXE
在 1024/2048/4096 三档的运行时验收。尚未形成跨显卡压力矩阵，不得把
本机当前视图自适应证据外推为“所有设备全幅 4096 已验证”。

## 现象

- 大范围 GeoTIFF 即使选择“精细 · 1024”，资源卡仍只显示约
  128 × 95、约一万顶点。
- 山脊和沟谷在大范围视图中被明显削平，边界侧墙呈粗块状。
- 质量下拉框没有 2048/4096，用户无法请求更高的当前视图细节。
- 旧 HUD 展示根概览尺寸，而不是当前真正参与绘制的流式几何量。

## 根因

### 1. 一个“分辨率”同时承担两个互相冲突的语义

前端把 `settings.resolution` 当作网格质量，但文件型大栅格的 Core 为控制
首帧成本，会把根概览强制约束在约 128 像元。流式 LOD 调度器又完全不读取
该设置，因此 256、512、1024 实际使用相同的误差阈值、层级和瓦片预算。

结果是下拉框改变了设置值，却没有改变大文件的实际几何权利。

### 2. 固定 24/56 瓦片预算无法兑现 1024 全幅质量

129 × 129 规则瓦片要覆盖等效长边：

- 256：4 个同级瓦片；
- 512：16 个同级瓦片；
- 1024：64 个同级瓦片；
- 2048：256 个同级瓦片；
- 4096：1024 个同级瓦片。

旧静止预算 56 连 1024 的完整同级覆盖都无法容纳。把预算直接提高到
1024 又会使现有 CPU 网格路径的显存和内存超过产品边界。

### 3. HUD 读取根层而非活动瓦片

旧资源卡用 `sampled.cols × sampled.rows` 和根层顶点数作为“分辨率/顶点”
展示。即使细节瓦片已经加载，也仍显示约 128 × N，无法区分“没有加载”
与“加载了但 HUD 没看见”。

### 4. Harness 只证明有瓦片，没有证明质量等级

旧运行时断言覆盖完成、队列归零和预算未超，但没有断言：

- 用户选择的目标长边；
- 实际到达的最大 LOD；
- 活动/目标瓦片的真实顶点与三角形数；
- 细节几何是否显著超过根概览。

因此低精度结果可以假绿。

## 根因级修复

1. 保留约 128 像元根概览，只承担快速首帧和加载期 fallback。
2. 将 256/512/1024/2048/4096 定义为屏幕空间误差驱动的流式质量档：
   - 256：最大 L1、静止 4 瓦片；
   - 512：最大 L2、静止 16 瓦片；
   - 1024：最大 L3、静止 64 瓦片；
   - 2048：最大 L4、静止 96 瓦片；
   - 4096：最大 L5、静止 128 瓦片。
3. 256/512/1024 可在完整视域内逐级兑现；2048/4096 是当前视图重点区域
   的自适应高精度，不承诺把整幅 DEM 同时构造成 2048²/4096² 单网格。
4. 继续保持 192 MiB GPU 几何硬上限；超过预算时保留较粗父层，不允许
   崩溃、上下文丢失或无提示地构建多 GiB 单网格。
5. 文件窗口解码最多两路并发；四路并发在指定 31,984 × 18,495 LZW TIFF
   的冷启动中会叠加解码工作缓冲，使进程树瞬时超过 1.5 GiB。
6. 文件型数据切换质量只重新调度瓦片，不重复构建不变的 128 根概览。
7. HUD 改为报告实际达到精度与目标精度，以及活动瓦片真实顶点数。
8. 运行时诊断增加目标层级、最大/最小 ready 层级、层级直方图、活动和
   ready 目标顶点/三角形、CPU/GPU 预算。
9. file-backed 根概览固定为 128；2048/4096 仅对 file-backed streaming
   数据开放，非流式图像/小数据最高 1024，杜绝 4096² 单网格误入主线程。
10. 根层完成覆盖且基座厚度为 0 时，根顶面和粗边界墙一起撤下；只有用户
    请求正厚度基座时才保留根边界墙，避免“0 m”仍显示 128 级柱墙。
11. 活动瓦片从根层插值得到多方向 horizon visibility；不得只给隐藏根网格
    写遮蔽 attribute、让真正显示的瓦片保持全 1。
12. 解码块缓存收紧到 64 MiB，overview 与双路瓦片解码错峰；Windows 在
    overview 结束后回收已不活跃的驻留页。

## 为什么不采用 4096² 单网格

4096² 约 1,678 万顶点。按当前 positions、colors、uv、horizon、index 及
构建中间数组估算，峰值会达到数 GiB；JavaScript 主线程构网还会产生长
时间停顿。这既不满足“大范围极致丝滑”，也没有与屏幕像素相称的视觉收益。

4096 档必须表示“当前视图可达到 L5”，而不是“同时驻留 4096² 顶点”。
后续若迁移为共享规则网格加高程纹理，可在不改变这五档产品语义的情况下
进一步降低 CPU/GPU 占用。

## 永久回归 Oracle

静态闸门必须证明：

- 五个质量选项都存在；
- 2048/4096 分别映射 L4/L5；
- 每档有独立 SSE 与交互/静止预算；
- 诊断包含目标、实际层级、真实顶点和 GPU 预算。

Release EXE 的真实 file-backed GeoTIFF 运行时必须证明：

- `targetMaxDimension` 等于 Harness 显式选择的档位；
- `maximumReadyLevel == targetMaxLevel`；
- `achievedMaxDimension >= targetMaxDimension`；
- `readyDesiredVertexCount > sampledLength`，细节几何不得退化为根概览；
- `coverageComplete=true`，父层替换完整；
- 厚度为 0 时 root 顶面和粗基座均关闭；正厚度时基座完整保留；
- 1024 档必须 `minimumReadyLevel == maximumReadyLevel == targetMaxLevel`，
  目标层直方图计数必须等于 ready 数量；
- 指定金样的 ready 三角形必须精确为 762,571，顶点不得少于 1,000,000；
- 所有 ready 瓦片都必须具有与其顶点数等长的 horizon attribute；
- request/upload 队列全部归零；
- `gpuBytes <= gpuBudgetBytes`；
- 完整进程树内存聚合必须可用且峰值不得超过 1.5 GiB；
- NoData 洞、掩膜指纹和有效区轮廓仍通过既有拓扑 Oracle。

HUD 文本、选择框值、文件名、普通 RAF 或“画面看起来更细”均不能替代这些
结构证据。

## 回滚

- 可删除 2048/4096 选项并恢复单一质量 profile。
- 可通过既有 `legacyFocusLod=1` 回到 root+focus 路径。
- 回滚不改变 DMT3、Core 公开命令、设置持久化格式、最近文件或源 DEM。
- 禁止以重新强制 128 根概览、填平 NoData 或构建 4096² 单网格作为回滚。
